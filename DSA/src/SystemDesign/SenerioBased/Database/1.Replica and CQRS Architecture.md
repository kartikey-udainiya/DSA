Payment status updated in the primary DB, but the read DB still shows PENDING. How do you fix it?

Question:
Payment status is updated to SUCCESS in the Primary Database, but the Read Database still shows PENDING. How would you identify and fix this issue?

1. Understand the Problem

First, I would identify why the data is inconsistent.

In a typical backend architecture, we may have:
- Primary Database (Write DB): Handles INSERT, UPDATE and DELETE operations.
- Read Database (Read Replica): Handles SELECT operations to reduce the load on the Primary DB.

For example:

A customer makes a payment.

Step 1: Payment service updates the Primary DB:
payment_id = 101
status = SUCCESS

Step 2: The user requests payment details.

Step 3: The application fetches data from the Read DB.

Step 4: The Read DB still returns:
payment_id = 101
status = PENDING

This happens because the Primary DB and Read DB are not synchronized immediately.

This is called Eventual Consistency.

The Read DB will eventually receive the latest changes, but there might be a delay.

2. Identify the Architecture

Before fixing the issue, I would identify which architecture is being used.

There are two common possibilities:

A. Primary Database + Read Replica

In this architecture, the database itself replicates changes from the Primary DB to the Read Replica.

Example:

Application
|
v
Primary DB (Write)
|
| Asynchronous Replication
v
Read Replica (Read)

When a payment is updated in the Primary DB, the database replication mechanism propagates that change to the Read Replica.

The problem occurs when replication takes time.

B. CQRS Architecture

CQRS stands for Command Query Responsibility Segregation.

It separates the write operations from the read operations.

- Command: Handles operations that modify data.
- Query: Handles operations that retrieve data.

Example:

Payment Service
|
v
Primary DB
|
v
Event Publisher
|
v
Kafka / RabbitMQ
|
v
Event Consumer
|
v
Read DB

Here, whenever a payment is updated, the application publishes an event.

A background consumer processes that event and updates the Read DB.

If event publishing or consumption is delayed, the Read DB shows stale data.

3. Solution for Primary DB + Read Replica

If we are using database replication, I would follow these steps:

A. Monitor Replication Lag

Replication lag is the time difference between when a change is committed to the Primary DB and when it becomes visible on the Read Replica.

For example:

10:00:00 - Payment updated to SUCCESS in Primary DB.
10:00:01 - User requests payment details.
10:00:01 - Read Replica still returns PENDING.
10:00:05 - Read Replica receives the latest update.

In this case, replication lag is approximately 5 seconds.

I would monitor replication lag and investigate whether it is caused by:
- High write traffic.
- Network latency.
- Slow replication processes.
- Read replica resource limitations.
- Large transactions.

B. Read from Primary DB for Critical Operations

If the user updates a payment and immediately requests its status, I would fetch the latest data from the Primary DB instead of the Read Replica.

Example:

Payment Update API:
-> Write to Primary DB.

Payment Status API:
-> Fetch from Primary DB immediately after the update.

Other normal read operations can continue using the Read Replica.

This approach is called Read-after-Write Consistency.

C. Improve Replication Performance

If replication lag is consistently high, I would:
- Optimize expensive write queries.
- Check database resource utilization.
- Improve network connectivity.
- Scale the read replicas if necessary.
- Investigate replication configuration and bottlenecks.

4. Solution for CQRS Architecture

If we are using CQRS, I would focus on making event publishing and consumption reliable.

The biggest problem here is that updating the Primary DB and publishing an event are two separate operations.

Consider this implementation:

Step 1: Update the Primary DB.

await db.payment.update({
where: { id: paymentId },
data: { status: "SUCCESS" }
});

Step 2: Publish an event.

await kafka.publish("payment.updated", {
paymentId,
status: "SUCCESS"
});

Problem with this implementation:

What if the database update succeeds but Kafka publishing fails?

For example:

1. Payment status is successfully updated to SUCCESS.
2. Application tries to publish the event.
3. Kafka is temporarily unavailable.
4. Event is never published.
5. Read DB continues showing PENDING.

Now we have inconsistent data.

This problem is called the Dual Write Problem.

To solve this, I would use the Transactional Outbox Pattern.

5. Transactional Outbox Pattern
The Transactional Outbox Pattern ensures that the database update and event creation happen atomically within a single database transaction.
Instead of directly publishing an event to Kafka, we first store the event in an Outbox table.

Example database tables:
Payments:
payment_id | status
101        | SUCCESS

Outbox:
event_id | payment_id | event_type      | published
501      | 101        | PAYMENT_UPDATED | false

Step 1: Start a database transaction.
Step 2: Update the payment status in the Payments table.
Step 3: Insert an event into the Outbox table.
Step 4: Commit the transaction.

Example:

BEGIN TRANSACTION;
UPDATE payments
SET status = 'SUCCESS'
WHERE payment_id = 101;

INSERT INTO outbox (
event_id,
payment_id,
event_type,
published
)
VALUES (
501,
101,
'PAYMENT_UPDATED',
false
);

COMMIT;

Now both operations succeed or fail together.
If the transaction fails, neither the payment update nor the Outbox event is committed.
If the transaction succeeds, both records are stored.

Step 5: Outbox Relay
A background worker continuously checks the Outbox table for unpublished events.

For example:
SELECT *
FROM outbox
WHERE published = false;

The worker retrieves the event and publishes it to Kafka or RabbitMQ.
After successful publishing, it marks the event as published.
This ensures that if Kafka is temporarily unavailable, the event remains safely stored in the database and can be published later.

Note:
There is still a possibility that the worker publishes an event successfully but crashes before marking it as published.
In that situation, the same event may be published again.

Therefore, we also need idempotent consumers.

6. Event Consumer and Read DB Update
Once Kafka receives the event, a consumer processes it.

Example event:
{
"eventId": "501",
"paymentId": "101",
"eventType": "PAYMENT_UPDATED",
"status": "SUCCESS",
"version": 2
}

The consumer receives the event and updates the Read DB.
Example:

async function processPaymentEvent(event) {

    await readDB.payment.update({
        where: {
            paymentId: event.paymentId
        },
        data: {
            status: event.status
        }
    });

}

Now the Read DB eventually shows SUCCESS.
However, we still need to handle failures and duplicate messages.

7. Idempotency (Prevent Duplicate Processing)

In distributed systems, we cannot always guarantee that a message will be delivered exactly once.
For example:

1. Kafka delivers an event to the consumer.
2. Consumer updates the Read DB successfully.
3. Consumer crashes before acknowledging the message.
4. Kafka delivers the same event again.

Without protection, the same event might be processed multiple times.
This is called Duplicate Message Processing.
To prevent this, I would implement Idempotency.

An operation is idempotent when executing it multiple times produces the same final result as executing it once.
For example:

Updating payment status to SUCCESS multiple times is safe if the operation is simply setting the same status.
However, operations such as deducting money must not execute repeatedly.

We can maintain a Processed Events table:

processed_events:

event_id | processed_at
501      | timestamp

Before processing an event:

1. Check whether the event ID already exists.
2. If it exists, skip processing.
3. Otherwise, update the Read DB.
4. Insert the event ID into processed_events.
5. Commit both operations in one database transaction.
6. Acknowledge the Kafka message.

This ensures duplicate events do not cause duplicate side effects.

8. Retry Mechanism and Dead Letter Queue

What happens if the consumer cannot update the Read DB?

For example:
- Read DB is unavailable.
- Database connection times out.
- Temporary network failure occurs.

I would implement a retry mechanism.

Instead of immediately retrying continuously, I would use Exponential Backoff.

Example:

First attempt: Immediately
Second attempt: After 2 seconds
Third attempt: After 4 seconds
Fourth attempt: After 8 seconds
Fifth attempt: After 16 seconds

I would also add jitter (a random delay) to avoid many workers retrying simultaneously.

What if the event continues failing?

After a configured number of attempts, I would move the event to a Dead Letter Queue (DLQ).

A DLQ stores messages that could not be processed successfully.

We can then:
- Investigate the failure.
- Check logs and error details.
- Fix the underlying issue.
- Replay the event after resolving the problem.

Important:
I would not silently discard failed payment events.

9. Event Ordering

Another important problem is event ordering.
Consider this scenario:

Payment status changes:

Event 1: PENDING
Event 2: SUCCESS

But because of asynchronous processing, events arrive in this order:

Event 2: SUCCESS
Event 1: PENDING

If the consumer processes both events without checking their order, the final Read DB status becomes PENDING.
This is incorrect.
To prevent this, I would use:

A. Version Numbers

Every payment update gets an incrementing version.
Example:

Event 1:
paymentId = 101
status = PENDING
version = 1

Event 2:
paymentId = 101
status = SUCCESS
version = 2

Before updating the Read DB, compare the incoming event version with the stored version.
Only process events with a newer version.

B. Kafka Partitioning
If using Kafka, I would use paymentId as the message key.
This ensures events for the same payment are sent to the same partition and preserves their partition order.
Version checks are still useful as additional protection against stale updates and replayed events.

10. Reconciliation Jobs

Even after implementing all these mechanisms, I would add a reconciliation process.
A reconciliation job periodically compares the Primary DB and Read DB to identify inconsistent records.

Example:
Primary DB:

payment_id = 101
status = SUCCESS

Read DB:

payment_id = 101
status = PENDING

The reconciliation job identifies this mismatch and triggers a correction.
Possible approaches:
- Reprocess the missing event.
- Fetch the latest payment data from the Primary DB.
- Update the Read DB.
- Record the correction for auditing.

For a payment system, reconciliation is particularly important because payment status must remain accurate.

11. Monitoring and Observability

I would also monitor the entire synchronization pipeline.
Important metrics:

1. Replication Lag:
   How long does the Read DB take to receive updates?

2. Consumer Lag:
   How many Kafka messages are waiting to be processed?

3. Failed Events:
   How many events failed processing?

4. Retry Count:
   How often are events being retried?

5. DLQ Messages:
   How many messages have moved to the Dead Letter Queue?

6. Event Processing Latency:
   How long does it take from event creation to Read DB update?

I would use structured logging and distributed tracing to track a payment across the Payment Service, Outbox Relay, Kafka and Read DB Consumer.

For a payment system using CQRS, I would design the flow like this:
Payment Service

Additional mechanisms:

- Idempotency: Prevent duplicate processing.
- Exponential Backoff: Retry temporary failures.
- DLQ: Store permanently failed events.
- Versioning: Prevent out-of-order updates.
- Reconciliation: Detect and repair inconsistencies.
- Monitoring: Track replication and consumer lag.

13. How I Would Explain This in an Interview

First, I would identify whether we are using database replication or CQRS.
If it is a read replica architecture, I would investigate replication lag and use the primary database for critical read-after-write operations.
If it is CQRS, I would investigate whether the event was successfully published and consumed.
For reliable synchronization, I would implement the Transactional Outbox Pattern. This ensures that the payment update and event creation happen in the same database transaction.

A background worker would publish the event to Kafka or RabbitMQ, and a consumer would update the Read DB.
I would also implement idempotency to handle duplicate messages, exponential backoff for retries, a Dead Letter Queue for failed events, versioning to maintain event ordering, and reconciliation jobs to identify any inconsistencies.
Since this is a payment system, I would always treat the write-side payment status as authoritative and never assume a payment failed simply because the Read DB has stale data.

The overall goal is to achieve reliable eventual consistency without losing payment events or processing financial operations more than once.
