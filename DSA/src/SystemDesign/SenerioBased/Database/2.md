Question: User updates their profile, refreshes the page, and still sees old data. Why does this happen, and how would you fix it?

1. Understand the Problem

Suppose a user updates their profile:

Old data:
{
"userId": 101,
"name": "Kartikey",
"city": "Pune"
}

The user changes their city from Pune to Bangalore.

The application successfully updates the database:

{
"userId": 101,
"name": "Kartikey",
"city": "Bangalore"
}

However, when the user refreshes the page, the application still displays:

{
"userId": 101,
"name": "Kartikey",
"city": "Pune"
}

This means the update may have succeeded, but the application is retrieving stale (outdated) data.

This problem can occur at different layers of the architecture:
- Database replication
- Application-level caching
- Browser caching
- CDN caching
- Asynchronous event processing
- Incorrect API or database query logic

Before fixing it, I would identify which layer is returning the old data.

2. Possible Reason 1: Database Replication Lag

If the application uses a Primary DB and Read Replica architecture, this is one of the most common reasons.

Architecture:

Application
|
v
Primary DB (Write)
|
| Asynchronous Replication
v
Read Replica (Read)

How does it happen?

Step 1: User updates their city to Bangalore.

Step 2: Application sends an UPDATE query to the Primary DB.

Step 3: Primary DB successfully commits the update.

Step 4: User refreshes the page.

Step 5: GET API fetches the profile from the Read Replica.

Step 6: Read Replica has not received the latest update yet.

Therefore, the API returns the old city: Pune.

Why does this happen?

In asynchronous replication, changes are not necessarily copied to replicas immediately.

The Primary DB commits the change first and replicates it to the Read Replica afterward.

This delay is called replication lag.

Solutions:

A. Read-after-Write Consistency

After a user updates their profile, fetch the latest data directly from the Primary DB instead of the Read Replica.

For example:

PUT /profile
-> Update Primary DB

GET /profile
-> Read from Primary DB immediately after update

For normal profile reads, continue using the Read Replica.

B. Session-based Consistency

Maintain information about recently updated records or users.

For example, after updating a profile, route that user's subsequent reads to the Primary DB for a short period.

This avoids stale reads without routing every user's request to the Primary DB.

C. Monitor Replication Lag

Monitor how much time the Read Replica takes to receive changes.

If replication lag is consistently high, investigate:
- Database CPU and memory utilization.
- Network latency.
- Heavy write transactions.
- Replication configuration.
- Replica resource limitations.

3. Possible Reason 2: Redis Cache Contains Old Data

Another common reason is caching.

Suppose the application uses Redis to cache user profiles.

Architecture:

Application
|
v
Redis
|
v
Primary DB

How does it happen?

Step 1: User requests their profile.

Step 2: Application fetches the profile from the database and stores it in Redis.

Redis:
{
"userId": 101,
"city": "Pune"
}

Step 3: User updates their city to Bangalore.

Step 4: Application successfully updates the Primary DB.

Step 5: However, Redis still contains the old profile.

Step 6: User refreshes the page.

Step 7: Application checks Redis first.

Step 8: Redis returns the old city: Pune.

The database contains Bangalore, but Redis returns Pune.

This problem is called Cache Invalidation or Cache Inconsistency.

Solutions:

A. Cache Invalidation

Whenever the profile is updated, invalidate the corresponding Redis cache entry.

Example:

// Update database
await db.user.update({
where: { id: 101 },
data: { city: "Bangalore" }
});

// Delete old Redis cache
await redis.del("user:101");

Now, when the user requests their profile again:
1. Application checks Redis.
2. Cache entry does not exist.
3. Application fetches fresh data from the database.
4. Application stores the updated profile in Redis.

B. Cache Update (Write-through approach)

Instead of deleting the cache, update Redis immediately after updating the database.

Example:

await db.user.update({
where: { id: 101 },
data: { city: "Bangalore" }
});

await redis.set(
"user:101",
JSON.stringify({
userId: 101,
city: "Bangalore"
})
);

Now Redis also contains the latest data.

However, database and Redis updates are separate operations, so failures can still cause inconsistency. We need retries or another synchronization mechanism if strict reliability is required.

C. TTL (Time To Live)

Set an expiration time on Redis keys.

For example:

EXPIRE user:101 300

This means the cache entry expires after 300 seconds (5 minutes).

After expiration, the application fetches fresh data from the database.

Important: TTL reduces how long stale data can remain, but it does not guarantee immediate consistency.

4. Possible Reason 3: CQRS and Eventual Consistency

If the application uses CQRS, the Write DB and Read DB are separate models.

Architecture:

Application
|
v
Command Handler
|
v
Write DB
|
v
Event Publisher
|
v
Kafka / RabbitMQ
|
v
Event Consumer
|
v
Read DB
|
v
Query Handler

How does it happen?

Step 1: User updates their profile.

Step 2: Command Handler updates the Write DB.

Step 3: An event called UserProfileUpdated is generated.

Step 4: Event is published to Kafka.

Step 5: Consumer receives the event.

Step 6: Consumer updates the Read DB.

Now imagine the user refreshes the page before the consumer processes the event.

The Query Handler fetches the profile from the Read DB, which still contains the old city.

This is called Eventual Consistency.

Solutions:

A. Transactional Outbox Pattern

The database update and event creation should happen within the same database transaction.

This prevents the situation where the profile update succeeds but the event is lost.

B. Retry Mechanism

If the consumer fails to update the Read DB, retry the event using exponential backoff.

C. Idempotency

Make sure processing the same UserProfileUpdated event multiple times does not cause incorrect results.

D. Read from Write DB

For critical read-after-write operations, fetch the profile directly from the Write DB instead of waiting for the Read DB to synchronize.

5. Possible Reason 4: Browser or CDN Caching

Sometimes the backend and database are perfectly correct, but the browser or CDN returns an old response.

How does it happen?

Step 1: User opens their profile.

Step 2: Browser or CDN caches the GET API response.

Step 3: User updates their profile.

Step 4: Database gets updated successfully.

Step 5: User refreshes the page.

Step 6: Browser or CDN serves the previously cached response instead of making a fresh request to the backend.

Solutions:

A. HTTP Cache-Control Headers

For sensitive or frequently changing profile data, configure suitable response headers.

Example:

Cache-Control: no-store

This instructs the browser and compliant caches not to store the response.

B. Cache Revalidation

For resources that can be cached, use ETag and conditional requests.

The browser can send an If-None-Match header to check whether the cached response is still valid.

C. CDN Cache Invalidation

If a CDN caches profile responses, invalidate the relevant cache when the profile is updated, or avoid caching user-specific responses at the CDN.

6. Possible Reason 5: Frontend State Management Issue

Sometimes the backend returns the correct updated profile, but the frontend continues displaying old data.

For example, the application uses:
- React state.
- Redux.
- React Query.
- SWR.

How does it happen?

Step 1: User opens their profile.

Step 2: Profile data is stored in frontend state.

Step 3: User updates their city to Bangalore.

Step 4: Backend successfully updates the database.

Step 5: Frontend state is not updated or its cached query is not invalidated.

Step 6: The UI continues displaying Pune.

Solutions:

A. Update Frontend State

After a successful API response, update the frontend state with the returned profile.

B. Invalidate Query Cache

If using React Query, invalidate the profile query after a successful update.

Example:

await updateProfile(data);

queryClient.invalidateQueries({
queryKey: ["profile"]
});

This tells React Query that the cached profile data is stale and should be refetched.

C. Refetch the Profile

After the update succeeds, make another GET request to fetch the latest profile data.

7. How Would I Debug This Issue in Production?

I would not immediately assume that the database is responsible.

I would follow this debugging sequence:

Step 1: Verify the Write Operation

Check whether the UPDATE query successfully committed to the Primary DB.

Step 2: Verify the Read Operation

Check which database the GET API is querying.

Is it querying the Primary DB or Read Replica?

Step 3: Check Replication Lag

If it uses a Read Replica, check whether replication has caught up.

Step 4: Check Redis

Check whether Redis contains the old profile data.

Step 5: Check Event Processing

If using CQRS, verify:
- Was the event generated?
- Was it published to Kafka?
- Was it consumed?
- Did the consumer successfully update the Read DB?
- Is there consumer lag or a failed message?

Step 6: Check HTTP Caching

Inspect browser network requests and response headers.

Check whether the response came from the browser cache, CDN, or backend.

Step 7: Check Frontend State

Verify whether the API returns updated data but the UI still displays stale state.

8. Monitoring and Prevention

I would introduce monitoring to detect these issues before users report them.

Important metrics:

1. Database Replication Lag:
   Measures how far behind the Read Replica is.

2. Redis Cache Hit/Miss Ratio:
   Helps identify caching behavior.

3. Event Consumer Lag:
   Measures how many Kafka messages are waiting to be processed.

4. Event Processing Failures:
   Tracks failed profile update events.

5. API Response Time:
   Helps identify slow database or cache operations.

6. Cache Invalidation Failures:
   Tracks cases where the database is updated but the cache is not invalidated.

I would also use structured logging and distributed tracing to track a profile update across the API, database, Redis, Kafka and consumer.

9. Final Recommended Approach

For a typical profile management application, I would use the following approach:

1. Update the profile in the Primary DB.
2. Invalidate the corresponding Redis cache after the database transaction succeeds.
3. For immediate reads after an update, fetch from the Primary DB.
4. Use Read Replicas for normal read operations.
5. If using CQRS, use the Transactional Outbox Pattern to reliably publish profile update events.
6. Implement idempotent consumers and retries.
7. Configure suitable HTTP caching policies for user-specific data.
8. Update or invalidate frontend query caches after successful mutations.
9. Monitor replication lag, cache consistency and event processing.

10. Interview Answer

First, I would identify which layer is returning stale data because this problem can occur at multiple levels.

If we use Primary DB and Read Replica architecture, the issue could be replication lag. The Primary DB may have committed the update, but the Read Replica has not received it yet. I would use read-after-write consistency by routing immediate reads to the Primary DB.

If Redis is involved, the cache might still contain the old profile. I would implement cache invalidation or cache updates after successful database writes.

If we use CQRS, the event might not have been consumed yet, meaning the Read DB has not caught up with the Write DB. I would investigate the event publishing and consumption pipeline and use the Transactional Outbox Pattern, retries and idempotent consumers.

I would also check browser caching, CDN caching and frontend state management to ensure the stale response is not coming from the client side.

Finally, I would add monitoring for replication lag, cache invalidation failures and Kafka consumer lag.

My goal would be to ensure read-after-write consistency for the user while maintaining scalability for normal read operations.
