Question: Two users update the same database record simultaneously. How do you prevent one user's changes from overwriting the other user's changes?

1. Understand the Problem
This problem is called a Race Condition or Concurrent Update Problem.
Suppose we have a user record:

users table:

user_id | name     | city
101     | Kartikey | Pune

Two users (or two application requests) try to update the same record simultaneously.
User A wants to update the city to Bangalore.
User B wants to update the name to Rahul.

Consider the following sequence:

Step 1: User A reads the existing record.

{
"userId": 101,
"name": "Kartikey",
"city": "Pune"
}

Step 2: User B reads the same existing record.

{
"userId": 101,
"name": "Kartikey",
"city": "Pune"
}

Step 3: User A modifies the city.

{
"userId": 101,
"name": "Kartikey",
"city": "Bangalore"
}

Step 4: User B modifies the name.

{
"userId": 101,
"name": "Rahul",
"city": "Pune"
}

Step 5: User A saves the entire record.

Database now contains:

{
"userId": 101,
"name": "Kartikey",
"city": "Bangalore"
}

Step 6: User B saves their entire record.

Database now contains:

{
"userId": 101,
"name": "Rahul",
"city": "Pune"
}

Problem:

User A's city update has been lost.
The final database record contains Rahul and Pune, even though User A successfully updated the city to Bangalore.
This is called a Lost Update Problem.

2. Solution 1: Optimistic Locking (Version-Based Locking)

Optimistic locking is one of the most common approaches to prevent lost updates.
The idea is simple: Before updating a record, check whether someone else has modified it since you last read it.
We maintain an additional version column in the database.

Example:

users table:

user_id | name     | city | version
101     | Kartikey | Pune | 1

Now let's understand how it works.

Step 1: User A reads the record.

{
"userId": 101,
"name": "Kartikey",
"city": "Pune",
"version": 1
}

Step 2: User B also reads the same record.

{
"userId": 101,
"name": "Kartikey",
"city": "Pune",
"version": 1
}

Both users have version 1.

Step 3: User A updates the city.

Instead of directly updating the record, we check whether the current version is still 1.

SQL:

UPDATE users
SET city = 'Bangalore',
version = version + 1
WHERE user_id = 101
AND version = 1;

The condition matches, so the update succeeds.

Database now contains:

user_id | name     | city      | version
101     | Kartikey | Bangalore | 2

Step 4: User B tries to update the name.

User B still has the old version (1).

SQL:

UPDATE users
SET name = 'Rahul',
version = version + 1
WHERE user_id = 101
AND version = 1;

But the database version is now 2.
Therefore, the WHERE condition does not match any record.
Affected rows = 0.
The database rejects the stale update.

Step 5: Handle the conflict.
The application detects that zero rows were updated.

It can:
- Return HTTP 409 Conflict.
- Fetch the latest record.
- Inform the user that someone else modified the record.
- Ask the user to review and retry their changes.

Important:
Optimistic locking does not lock the record while users are editing it.
It allows multiple users to read and work on the same record, but checks for conflicts when they try to save.
This is useful when simultaneous updates are relatively uncommon.

3. Solution 2: Pessimistic Locking (Database-Level Locking)
Another approach is pessimistic locking.
Instead of allowing multiple users to update the record and detecting conflicts afterward, we lock the record while a transaction is modifying it.
This prevents other transactions from modifying the same record until the lock is released.

We commonly use SELECT FOR UPDATE.

Example:

BEGIN;

SELECT *
FROM users
WHERE user_id = 101
FOR UPDATE;

UPDATE users
SET city = 'Bangalore'
WHERE user_id = 101;

COMMIT;

How does it work?

Step 1: User A starts a transaction.
Step 2: User A executes SELECT FOR UPDATE.
Step 3: Database acquires an exclusive row-level lock on that record.
Step 4: User B tries to update the same record.
Step 5: User B must wait until User A's transaction completes.
Step 6: User A commits the transaction.
Step 7: The database releases the lock.
Step 8: User B can now proceed.

Example:

User A:
Acquire lock
Update city
Commit
Release lock

User B:
Try to acquire lock
Wait for User A
Acquire lock
Read latest data
Update record
Commit

Advantages:

- Prevents concurrent modification during the transaction.
- Useful for highly contested records.
- Ensures serialized updates to the locked row.

Disadvantages:

- Requests may have to wait.
- Too many locks can reduce performance.
- Can lead to deadlocks if transactions acquire locks in different orders.
- Long-running transactions can block other requests.

Important:

Never hold a database row lock while waiting for a user to edit a form. Keep the transaction short.

4. Solution 3: Atomic Database Updates
Sometimes the problem can be solved by avoiding the read-modify-write pattern altogether.
For example, suppose two users are incrementing the same account's points.

Incorrect approach:

Step 1: User A reads points = 100.
Step 2: User B reads points = 100.
Step 3: User A calculates 100 + 10 = 110.
Step 4: User B calculates 100 + 20 = 120.
Step 5: User A writes 110.
Step 6: User B writes 120.

Final points = 120.

But the correct result should be 130.

Instead, perform an atomic database operation:

UPDATE users
SET points = points + 10
WHERE user_id = 101;

And for User B:

UPDATE users
SET points = points + 20
WHERE user_id = 101;

The database executes these operations atomically.

Final points = 130.

The important difference is that we are not reading the old value into application memory and then writing a calculated replacement.
The database performs the increment directly.

Atomic updates are particularly useful for:
- Counters.
- Inventory adjustments.
- Wallet balances.
- Likes and views.
- Stock quantity changes.

For financial operations, I would additionally use database transactions, appropriate constraints and concurrency controls.

5. Solution 4: Database Transactions and Isolation Levels
Database transactions help ensure that multiple operations execute reliably.

A transaction follows ACID properties:

A. Atomicity:
Either all operations succeed or all operations fail.

B. Consistency:
The database remains in a valid state.

C. Isolation:
Concurrent transactions should not interfere in ways that violate the chosen isolation guarantees.

D. Durability:
Once committed, changes are persisted.

Isolation levels determine how concurrent transactions interact.

Common isolation levels:

1. Read Uncommitted:
   Allows reading uncommitted changes from other transactions.
   Can cause dirty reads.

2. Read Committed:
   Only reads committed data.
   Prevents dirty reads but does not automatically prevent lost updates.

3. Repeatable Read:
   Provides consistent repeated reads within a transaction, depending on the database implementation.
   May prevent certain concurrent update anomalies.

4. Serializable:
   Provides the strongest isolation by making concurrent transactions behave as if they executed sequentially.
   May introduce transaction retries and reduced concurrency.

Important:

Simply using a database transaction does not automatically prevent lost updates.
We need to choose the correct isolation level or use optimistic/pessimistic locking depending on the use case.

6. Solution 5: Unique Constraints and Database Constraints
Some concurrency problems can be prevented using database constraints.
For example, suppose two users simultaneously try to register with the same email address.
Both requests check whether the email exists.

Both find that it does not exist.
Both attempt to insert the same email.
Without a database constraint, duplicate records might be created.

Solution:

CREATE UNIQUE INDEX unique_email
ON users(email);

Now the database guarantees that duplicate email addresses cannot be inserted, even when multiple requests arrive simultaneously.
The application should handle the constraint violation and return an appropriate response.

Other useful constraints include:
- UNIQUE constraints.
- Foreign key constraints.
- CHECK constraints.
- NOT NULL constraints.

These protect data integrity at the database level.

7. How to Choose the Right Approach?
Different situations require different concurrency-control mechanisms.

A. Optimistic Locking:
Use when conflicts are relatively rare.

Examples:
- User profile updates.
- Document editing.
- Product information updates.
- Employee records.

B. Pessimistic Locking:
Use when conflicts are frequent and concurrent modifications must be serialized.

Examples:
- Inventory reservation.
- Financial account operations.
- Limited-seat booking.

C. Atomic Updates:
Use when operations can be performed directly by the database without application-level read-modify-write logic.

Examples:
- Incrementing counters.
- Decrementing stock.
- Updating balances with appropriate safeguards.

D. Database Constraints:
Use when a particular data rule must always be enforced.

Examples:
- Unique email.
- Unique order number.
- Valid inventory quantity.

8. Real-World Example: E-commerce Inventory Management
Suppose an e-commerce platform has only one product remaining. 
Current inventory:

product_id | stock
101        | 1

Two customers try to purchase the same product simultaneously.
Without proper concurrency control:

1. Customer A reads stock = 1.
2. Customer B reads stock = 1.
3. Customer A checks stock > 0.
4. Customer B checks stock > 0.
5. Both place an order.
6. Two orders are created for one available item.

This is called Overselling.

Solution:

Use an atomic conditional update.

SQL:

UPDATE products
SET stock = stock - 1
WHERE product_id = 101
AND stock > 0;

Now:

- Customer A executes the query first.
- Stock changes from 1 to 0.
- Customer B executes the same query.
- The condition stock > 0 fails.
- Zero rows are updated.
- Customer B receives an out-of-stock response.

This ensures that only one customer can reserve the available item.
For a real order system, I would perform the stock reservation and order creation within an appropriate database transaction.

9. How I Would Explain This in an Interview

First, I would identify whether the application has a Lost Update Problem.
For example, two users might read the same record, modify different fields and then save their entire records. 
The second update could overwrite the first user's changes.
My preferred approach for ordinary profile updates would be Optimistic Locking using a version column.
Whenever a user reads a record, we return its current version. During the update, 
we include that version in the WHERE condition and increment it if the update succeeds.
If another user has already modified the record, the version will have changed and the update will affect zero rows. 
I would then return a 409 Conflict response and ask the client to refresh or resolve the conflict.

For highly contested records, I would consider Pessimistic Locking using SELECT FOR UPDATE, 
which makes concurrent transactions wait for the current transaction to finish.

For counters and inventory, I would prefer atomic conditional database updates rather than reading and modifying values in application memory.
I would also use database constraints to enforce important business rules and transactions to maintain data integrity.

10. Important Concepts to Remember

- Race Condition: Multiple operations execute concurrently and their timing affects the result.
- Lost Update: One transaction overwrites another transaction's changes.
- Optimistic Locking: Detect conflicts using version numbers.
- Pessimistic Locking: Lock records to prevent concurrent modifications.
- SELECT FOR UPDATE: Acquires row-level locks within a transaction.
- Atomic Update: Performs a database modification as a single atomic operation.
- ACID: Atomicity, Consistency, Isolation and Durability.
- Isolation Levels: Control how concurrent transactions interact.
- Deadlock: Transactions wait for each other's locks indefinitely until the database detects and resolves the cycle.
- HTTP 409 Conflict: Indicates that the request conflicts with the current resource state.

The key takeaway:

For most profile update scenarios, I would start with Optimistic Locking.

For highly contested resources such as inventory or financial records, I would consider atomic conditional updates, database transactions and appropriate locking mechanisms.
