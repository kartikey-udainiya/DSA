# Database Transactions and Isolation Levels

## 1. What is a Database Transaction?

A database transaction is a group of database operations that are executed as one logical unit.

A transaction ensures that multiple operations are completed reliably.

Example: Suppose we want to transfer ₹2,000 from Account A to Account B.

There are two operations:

1. Deduct ₹2,000 from Account A.
2. Add ₹2,000 to Account B.

Both operations must succeed. If one operation fails, the entire transaction should be rolled back.

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 2000
WHERE account_id = 'A';

UPDATE accounts
SET balance = balance + 2000
WHERE account_id = 'B';

COMMIT;
```

If something fails:

```sql
ROLLBACK;
```

The database undoes the changes made by the transaction.

Without transactions, one operation might succeed while another fails, leaving the database in an inconsistent state.

## 2. ACID Properties

ACID represents four properties that make database transactions reliable.

### A. Atomicity

Atomicity means all operations within a transaction must succeed together or fail together.

It follows the all-or-nothing principle.

Example:

Suppose Account A has ₹10,000 and Account B has ₹5,000.

We want to transfer ₹2,000 from A to B.

Two operations are required:

- Deduct ₹2,000 from A.
- Add ₹2,000 to B.

If both operations succeed:

- Account A = ₹8,000
- Account B = ₹7,000

If the first operation succeeds but the second operation fails, the database rolls back the first operation.

The final balances remain:

- Account A = ₹10,000
- Account B = ₹5,000

This ensures that money does not disappear or get partially transferred.

### B. Consistency

Consistency means every committed transaction must leave the database in a valid state according to its defined rules and constraints.

Example:

Suppose a bank has a business rule:

Account balance cannot be negative.

An account currently has ₹1,000.

A user tries to withdraw ₹2,000.

The database should reject this operation because it violates the defined rule.

We can enforce this using a database constraint:

```sql
ALTER TABLE accounts
ADD CONSTRAINT balance_non_negative
CHECK (balance >= 0);
```

Now the database will not accept a negative balance.

Consistency ensures that transactions do not violate database constraints or implemented business rules.

Important: The database cannot automatically understand every business rule. Developers must implement the necessary validations and constraints.

### C. Isolation

Isolation determines how concurrent transactions interact with each other.

Concurrent transactions are transactions that execute at overlapping times.

Example:

Two users are trying to withdraw money from the same bank account.

Initial balance:

```text
balance = ₹10,000
```

Both users want to withdraw ₹7,000.

If both transactions read the balance at the same time, both might see ₹10,000.

Both may calculate the remaining balance as ₹3,000.

Both then update the database with ₹3,000.

The final balance becomes ₹3,000, even though two withdrawals of ₹7,000 were requested.

This is a concurrency problem.

Isolation levels determine what one transaction can read from another transaction and which concurrent operations are allowed.

### D. Durability

Durability means once a transaction is successfully committed, its changes should persist even if the database server crashes or restarts.

Example:

A user transfers ₹2,000 successfully.

The database returns:

```text
Transaction successful.
```

Immediately after that, the database server crashes.

When the server restarts, the transfer should still be recorded.

Databases generally achieve durability using transaction logs and persistent storage.

## 3. Why Do We Need Isolation Levels?

Imagine two transactions:

- Transaction A
- Transaction B

Both are accessing the same database records.

Without proper isolation, several problems can occur:

1. Dirty Read
2. Non-repeatable Read
3. Phantom Read
4. Lost Update

Isolation levels define which of these problems the database prevents or permits.

There are four commonly discussed SQL isolation levels:

1. Read Uncommitted
2. Read Committed
3. Repeatable Read
4. Serializable

## 4. Read Uncommitted

Read Uncommitted is the weakest standard SQL isolation level.

It allows a transaction to read changes made by another transaction even before those changes are committed.

This can cause a problem called Dirty Read.

Example:

Initially, the product stock is 10.

Transaction A:

```sql
BEGIN;

UPDATE products
SET stock = 0
WHERE id = 101;
```

Transaction A has updated the stock but has not committed the transaction.

Transaction B:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 101;
```

Transaction B might read:

```text
stock = 0
```

But something goes wrong in Transaction A.

Transaction A executes:

```sql
ROLLBACK;
```

The stock returns to:

```text
stock = 10
```

However, Transaction B has already read the value 0.

This is called a Dirty Read.

Why is it called Dirty Read?

Because Transaction B read data that was never committed and was eventually rolled back.

Real-world example:

A payment service reads a payment status as SUCCESS from an uncommitted update. Another transaction later rolls back that update.

The payment service has now acted on a value that was never permanently committed.

Key points:

- Allows reading uncommitted data.
- Can cause dirty reads.
- Does not provide strong consistency guarantees.
- Generally avoided in applications where correctness is important.

## 5. Read Committed

Read Committed is a commonly used isolation level and is the default in databases such as PostgreSQL.

It ensures that a transaction can only read committed data.

It prevents Dirty Reads.

Example:

Initially:

```text
stock = 10
```

Transaction A:

```sql
BEGIN;

UPDATE products
SET stock = 0
WHERE id = 101;
```

Transaction A has not committed yet.

Transaction B:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 101;
```

Transaction B sees:

```text
stock = 10
```

Why?

Because Transaction A's update is not committed yet.

Now Transaction A executes:

```sql
COMMIT;
```

If Transaction B executes the SELECT query again, it can now see:

```text
stock = 0
```

This prevents Dirty Reads.

However, Read Committed has another problem called Non-repeatable Read.

### Non-repeatable Read

A Non-repeatable Read occurs when the same transaction reads the same database row multiple times and gets different values because another transaction modified and committed that row between the reads.

Example:

Initially:

```text
stock = 10
```

Transaction B:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 101;
```

Result:

```text
stock = 10
```

Meanwhile, Transaction A updates the stock:

```sql
BEGIN;

UPDATE products
SET stock = 5
WHERE id = 101;

COMMIT;
```

Now Transaction B executes the same SELECT query again:

```sql
SELECT stock
FROM products
WHERE id = 101;
```

Result:

```text
stock = 5
```

The same transaction has received two different values for the same row.

This is called a Non-repeatable Read.

Why does this happen?

Because Read Committed guarantees that every read sees committed data, but it does not guarantee that repeated reads within one transaction see the same version of a row.

Key points:

- Prevents Dirty Reads.
- Allows Non-repeatable Reads.
- Allows Phantom Reads.
- Does not automatically prevent every Lost Update scenario.

## 6. Repeatable Read

Repeatable Read provides stronger isolation than Read Committed.

It aims to ensure that if a transaction reads the same row multiple times, it sees a consistent value for that row.

Example:

Initially:

```text
stock = 10
```

Transaction B:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 101;
```

Result:

```text
stock = 10
```

Meanwhile, Transaction A updates the stock:

```sql
BEGIN;

UPDATE products
SET stock = 5
WHERE id = 101;

COMMIT;
```

Now Transaction B executes the same SELECT query again:

```sql
SELECT stock
FROM products
WHERE id = 101;
```

Under snapshot-based Repeatable Read, Transaction B still sees:

```text
stock = 10
```

Why?

Because Transaction B continues reading from a consistent database snapshot instead of seeing the newly committed changes from Transaction A.

After Transaction B commits and starts a new transaction, it can see:

```text
stock = 5
```

This prevents Non-repeatable Reads in snapshot-based implementations.

Important:

Repeatable Read behavior differs across database engines.

For example:

- PostgreSQL uses snapshot isolation for Repeatable Read.
- MySQL InnoDB has its own implementation and locking behavior.

Also, Repeatable Read does not universally prevent every possible concurrent update anomaly. Always understand the behavior of the database you are using.

Key points:

- Prevents Dirty Reads.
- Prevents Non-repeatable Reads.
- Phantom Read behavior depends on the database implementation.
- Provides a consistent view of data within a transaction in snapshot-based implementations.

## 7. Serializable

Serializable is the strongest standard SQL isolation level.

It guarantees that concurrent transactions behave as though they were executed one after another in some serial order.

The database may still execute transactions concurrently internally, but their final outcome must be equivalent to a valid sequential execution.

Example:

Initial bank balance:

```text
balance = ₹10,000
```

Two users want to withdraw ₹7,000 each.

Without proper protection:

- Transaction A reads ₹10,000.
- Transaction B reads ₹10,000.
- Both calculate the remaining balance as ₹3,000.
- Both attempt to update the balance.

This can produce an incorrect result.

Under Serializable isolation, the database ensures that the result is equivalent to a sequential execution.

For example:

1. Transaction A executes first.
2. A withdraws ₹7,000.
3. Balance becomes ₹3,000.
4. Transaction B attempts to withdraw ₹7,000.
5. B cannot withdraw because only ₹3,000 is available.
6. B is rejected or must be retried after a serialization conflict.

Final balance:

```text
balance = ₹3,000
```

Only one withdrawal succeeds.

Important:

Serializable does not necessarily mean the database physically executes one transaction at a time.

Depending on the database implementation, it may:

- Make a transaction wait.
- Detect a serialization conflict and abort a transaction.
- Require the application to retry an aborted transaction.

Key points:

- Prevents Dirty Reads.
- Prevents Non-repeatable Reads.
- Prevents Phantom Reads.
- Provides the strongest standard SQL isolation guarantee.
- Can reduce concurrency.
- May introduce transaction retries and additional overhead.

## 8. Comparison of Isolation Levels

| Isolation Level | Dirty Read | Non-repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | Possible | Possible | Possible |
| Read Committed | Prevented | Possible | Possible |
| Repeatable Read | Prevented | Prevented | Depends on implementation |
| Serializable | Prevented | Prevented | Prevented |

These are standard SQL guarantees. Actual implementation details can vary between database engines.

## 9. Understanding the Four Concurrency Problems

### A. Dirty Read

A transaction reads data written by another transaction before it has been committed.

Example:

Transaction A updates stock from 10 to 0 but does not commit.

Transaction B reads stock as 0.

Transaction A rolls back.

Transaction B has read data that never became permanent.

### B. Non-repeatable Read

A transaction reads the same row twice but gets different values because another transaction updated and committed that row.

Example:

Transaction B reads stock as 10.

Transaction A changes stock to 5 and commits.

Transaction B reads again and gets 5.

### C. Phantom Read

A transaction executes the same query twice but receives a different set of rows because another transaction inserted or deleted rows matching the query condition.

Example:

Transaction B:

```sql
BEGIN;

SELECT *
FROM products
WHERE price > 1000;
```

It receives 5 products.

Meanwhile, Transaction A inserts another product:

```sql
INSERT INTO products (name, price)
VALUES ('Laptop', 50000);

COMMIT;
```

Transaction B executes the same query again.

It now receives 6 products under an isolation level that permits phantom reads.

The newly appearing matching row is called a Phantom Row.

### D. Lost Update

A Lost Update occurs when two transactions read the same old value, independently modify it, and one transaction overwrites the other's change.

Example:

Initial record:

```text
name = kartik
city = pune
```

User A reads the record.

User B reads the same record.

User A wants:

```text
name = abhishek
city = pune
```

User B wants:

```text
name = kartikey
city = delhi
```

Both users have an old copy of the record.

A saves first:

```text
name = abhishek
city = pune
```

B then saves its entire old copy with its modifications:

```text
name = kartikey
city = delhi
```

Final record:

```text
name = kartikey
city = delhi
```

User A's name update is lost.

This is called a Lost Update.

Important: A transaction alone does not automatically prevent Lost Updates. Protection depends on the isolation level, database implementation, locking strategy, and update method.

## 10. How Do We Prevent Lost Updates?

There are several approaches.

### A. Optimistic Locking

Optimistic locking uses a version number to detect whether another user has modified a record.

Example database record:

```text
id = 101
name = kartik
city = pune
version = 1
```

User A and User B both read version 1.

User A updates the record:

```sql
UPDATE users
SET name = 'abhishek',
    version = version + 1
WHERE id = 101
AND version = 1;
```

The update succeeds.

The database now contains:

```text
name = abhishek
city = pune
version = 2
```

User B tries to update using version 1:

```sql
UPDATE users
SET name = 'kartikey',
    city = 'delhi',
    version = version + 1
WHERE id = 101
AND version = 1;
```

This update affects zero rows because the current version is 2, not 1.

The application detects the conflict and can return:

```text
HTTP 409 Conflict
```

User B must fetch the latest record and decide whether to merge or retry the changes.

Optimistic locking is useful when conflicts are relatively rare.

### B. Pessimistic Locking

Pessimistic locking locks a database record so another transaction cannot modify it concurrently while the lock is held.

Example:

```sql
BEGIN;

SELECT *
FROM users
WHERE id = 101
FOR UPDATE;
```

The database acquires a row-level lock.

Other transactions attempting to acquire a conflicting lock must wait.

The application should then read the latest record, make the required changes, and commit.

Example:

User A acquires the lock and changes the name.

User B waits.

After A commits, B acquires the lock and reads the latest record.

B changes only the city.

Final record:

```text
name = abhishek
city = delhi
```

Important: If B uses its previously fetched stale copy and replaces the entire record, a lost update can still happen. Pessimistic locking does not automatically refresh data already held in application memory.

Pessimistic locking is useful when conflicts are frequent or when a resource is highly contested.

### C. Atomic SQL Updates

Atomic updates perform an operation directly in the database instead of reading a value into the application, modifying it, and writing it back.

Example:

Instead of:

1. Read stock.
2. Decrease stock in application code.
3. Save the new stock.

Use:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 101
AND stock > 0;
```

The database performs the operation atomically.

Only one update can successfully consume the final available unit.

Always check the affected row count to know whether the operation succeeded.

This is useful for:

- Inventory management.
- Counters.
- Account balances.
- Points and rewards.
- Stock reservation.

### D. Database Constraints

Constraints enforce rules at the database level.

Example:

Two users should not have the same email address.

```sql
ALTER TABLE users
ADD CONSTRAINT unique_email
UNIQUE (email);
```

Even if two requests attempt to insert the same email simultaneously, the database allows only one to succeed.

Constraints are important for protecting data integrity under concurrency.

## 11. Which Approach Should We Use?

| Scenario | Recommended Approach |
|---|---|
| User profile updates | Optimistic locking |
| Document editing | Optimistic locking |
| Highly contested inventory | Atomic updates and appropriate locking |
| Seat booking | Transactions, conditional updates, and locking |
| Bank balance updates | Atomic updates, transactions, and appropriate isolation |
| Unique email registration | Unique database constraint |
| Frequently contested records | Consider pessimistic locking |

The correct choice depends on how frequently conflicts occur and what the application needs to guarantee.

## 12. Important Interview Points

1. A transaction groups multiple database operations into one logical unit.
2. ACID stands for Atomicity, Consistency, Isolation, and Durability.
3. Atomicity means all operations succeed or all are rolled back.
4. Consistency means committed transactions preserve defined database rules.
5. Isolation determines how concurrent transactions interact.
6. Durability means committed changes persist.
7. Read Uncommitted can cause Dirty Reads.
8. Read Committed prevents Dirty Reads but allows Non-repeatable Reads.
9. Repeatable Read provides consistent repeated reads, with implementation-specific behavior.
10. Serializable provides the strongest standard SQL isolation guarantee.
11. A Dirty Read means reading uncommitted data.
12. A Non-repeatable Read means reading the same row twice and getting different values.
13. A Phantom Read means the same query returns a different set of matching rows.
14. A Lost Update means one transaction overwrites another transaction's changes.
15. Transactions alone do not automatically prevent all concurrency problems.
16. Optimistic locking detects conflicts using version numbers.
17. Pessimistic locking prevents conflicting operations while a lock is held.
18. Atomic SQL updates avoid application-level read-modify-write races.
19. Database constraints protect important data integrity rules.
20. Serializable transactions may need retries after serialization failures.

## 13. Final Concept to Remember

Think about these concepts in the following way:

- Transaction: Groups operations into one reliable unit.
- ACID: Defines the reliability properties of transactions.
- Isolation: Controls how transactions interact.
- Isolation Levels: Define the concurrency guarantees provided by the database.
- Optimistic Locking: Detects conflicting updates.
- Pessimistic Locking: Locks records to control concurrent access.
- Atomic Updates: Perform changes directly and safely inside the database.
- Constraints: Prevent invalid data from being stored.

The most important interview takeaway:

A transaction does not automatically solve every concurrency problem. We must select the appropriate isolation level and use locking, version checks, atomic updates, and database constraints according to the business requirement.
